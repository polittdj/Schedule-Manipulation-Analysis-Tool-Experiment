## OR-11e — the lever ADR-0480 refused, shipped with the evidence that made the refusal correct

ADR-0480 detected a partly-read prompt and named a remedy **the tool could not perform** (`OLLAMA_CONTEXT_LENGTH`, on the server, then restart it). This sends `num_ctx` — but only when the operator sets one. `AIConfig.num_ctx = 0` (the default) omits the key entirely, so the request is byte-for-byte what every install sent before; a non-zero value is clamped at **all three** boundaries it can enter by (form POST, settings file, backend constructor) into `[2048, 262144]`. The ceiling is **not ours**: 262,144 is Ollama's own `>= 48 GiB` tier default (`ollama/ollama#14073`), so the tool can never ask for more than the reference implementation hands the biggest machine — a **bound, not a safety guarantee**, since that issue's 52 GB-VRAM machine was at that very number. `_num_ctx_cost_note` states the mechanism, the `OLLAMA_NUM_PARALLEL` multiplier, the tier defaults as calibration, the incident **attributed**, and what is actually in force ("the tool sends no window" vs "asks for N") — and deliberately gives **no GB-per-token figure**, because the tool never reads the model's KV geometry and a fabricated number on a hardware-sizing page is worse than none. The cross-check model gets the same window (it reads the same fact sheet). `GenerationStats.num_ctx_sent` keeps ADR-0480's disclosure true against its own product: it now names the window already requested instead of telling an operator to raise what they raised.

**UNVERIFIED and claimed nowhere in the product:** what the server DOES on receipt. No Ollama in this container; ADR-0480 already recorded the truncation semantics as not verbatim-confirmed. What is proven is what LEAVES the tool. The UI says "asking is not allocating — the server decides, and it may refuse or cap it", which is the strongest honest statement available.
