# LAW 2 IMPACT — which fixes move a number the analyst has already been shown

**Date:** 2026-07-29
**Commit:** `9a1e5601746c3d5fc1f1ca97c9a12bd517a6fca1`

Law 2 (fidelity over speed): numbers must match the reference tools on the same inputs, and parity
is gate-locked. A fix that changes a **displayed** figure is therefore an ADR event with a golden
update and a `pytest -m parity` re-run — not a quiet patch.

**Reading rule for this document:** "changes a displayed number" means *for the input shapes named*.
None of these defects fire on a well-formed schedule with a resolvable calendar, present cost
columns, and a morning project start — which is why the existing golden fixtures are expected to be
unaffected. That expectation is **stated, not verified**: I did not run `pytest -m parity` (see
"What I did not do" below), and confirming it is the first step of any fix.

### The two that must move together

**V5 and V6 are a single ADR, not two.** Verified by execution
(`/tmp/audit-verify/lead_v5_adjudicate.py`):

```
booked 960 min/day against a DECLARED-ZERO-capacity crew (load > 1 unit-day)
   SHIPPED (or 1.0):        cap= 480.0 load= 960.0 over=True
   `or 1.0` REMOVED only:   cap=   0.0 load= 960.0 over=False
   => flag LOST  <-- removing line 171 alone SUPPRESSES a real over-allocation
```

Fixing `resources.py:171` on its own moves the "Over-allocated resources" KPI **the wrong way**,
because `over_allocated` requires `capacity_minutes > 0`. Any ADR must carry both lines.

### Ranking, by forensic exposure rather than by code size

1. **CC-02** — a false HIGH-severity accusation of concealment, indistinguishable from the true
   positive, triggered by an ordinary export-settings difference. In a testimony context this is the
   most damaging defect in the set: it is not a wrong number, it is a wrong *allegation*, and the
   tool's own output instructs the analyst to investigate "expenditure being hidden or moved".
2. **CC-01** — dates that fall on non-working days at 01:00 on a Mon–Fri 8-hour project. Facially
   indefensible in cross-examination, and effectively guaranteed on 20h/24h calendars.
3. **V6 + V5** — real over-allocation reported as none.
4. **V4 / V7** — a silently wrong calendar rescales every duration by 25–50%.
5. **V3** — a silently wrong filtered population under an elapsed literal.
6. **V1 / V2** — operator-input defects; the figure is wrong because the input was silently mangled.

### The borderline cases, called out rather than buried

The count/percentage divisors (`makeup.total or 1`, `len(tasks) or 1`, sweep group C and the three
UNSURE rows) sit between the groups. Fixing them to render "—" instead of `0.0%` on an empty
population **would** change what is displayed — from a fabricated `0.0%` to NA. That is a Law-2
*improvement*, but it is still a displayed-output change and should be ADR'd, not slipped in. It
would also close the inconsistency where `engine/metrics/dcma14.py:474-494` returns
`NOT_APPLICABLE` for exactly this case while the web layer prints `0.0%`.

## What I did NOT do (so this is not read as more than it is)

* **I did not run `pytest -m parity`, or any part of the gate.** The claim that the golden fixtures
  are unaffected is a reasoned expectation from the input shapes involved, not a measured result.
* **I did not fix anything.** No repo source file was modified — per instruction.
* **I did not verify the render path** for the three UNSURE sweep rows, so I cannot say whether a
  fabricated `0.0%` actually reaches the analyst there or is suppressed upstream.
* **I could not check CC-05 against the reference tool.** Whether SSI floors or truncates negative
  sub-day slack decides whether CC-05 is a code fix or a docstring fix. The goldens carry exact day
  multiples, so parity cannot tell them apart.

## Recommended sequencing, if these are taken forward

1. **CC-02 first**, alone, with its own ADR. It is the highest forensic exposure, the fix is
   local (`is None` checks in place of `or 0`), and it needs a golden update only for fixtures that
   carry present-then-absent cost/work — likely none.
2. **CC-01 next**, with V6's `or [sd]` and the `capacity_minutes > 0` guard folded in as dependents,
   since CC-01 is their root cause. This is the largest blast radius (74 call sites) and deserves a
   Fable-5-Max deep dive on the CPM date machinery before any edit.
3. **V5 + V6 together** (see above — never separately).
4. **V4 / V7** as one "malformed calendar should fail loud" ADR, since they are the same decision
   asked twice: does a bad calendar stop the import or get guessed?
5. **V1 / V2** as one SRA input-validation ADR.
6. **V3** last — it needs a product decision (add an elapsed axis, or reject elapsed literals with a
   message) before any code changes.
